# Feature Specification: README Hero GIF Refinement

**Feature Branch**: `development` (repo policy: single AI staging branch; no feature branch created)
**Created**: 2026-07-10
**Status**: Draft
**Input**: User description: "Revised CHILmesh README hero GIF (scripts/generate_hero_animation.py → docs/gallery/readme_pipeline_annulus.gif): (1) suppress massively degenerate/overlapping oversized elements visible in middle ADMESH truss iterations; (2) fix apparent speed-up toward end of truss convergence — uniform perceived pacing; (4) longer pause between each of the 4 stages; (5) redesign peel stage: on final smoothed mesh, reveal one layer at a time from boundary inward with a pause per layer, recoloring that layer's elements to the layer colormap while the corresponding portion of the quality histogram converts via stacked bars; (6) green dotted histogram line's metric text highlighted green in every frame; (7) second metric gets red dotted vertical line + red-highlighted text in every frame."

## Context

The README hero animation (`docs/gallery/readme_pipeline_annulus.gif`, generated by
`scripts/generate_hero_animation.py`) shows the CHILmesh pipeline on an annulus in four
stages: **Seed** (nodes fall onto the paper) → **ADMESH Truss** (real solver-iteration
playback) → **FEM Smoother** → **Peel Layers**. A binding prior operator mandate holds:
the truss stage must play back *actual* solver iterations (captured via the
`history_out=` hook), never interpolated fakes. The operator reviewed the current GIF
and identified six visual defects/improvements, specified below.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Clean truss playback (Priority: P1)

A README visitor watches the ADMESH truss stage and sees a scattered point cloud relax
into a quality mesh. Today, several mid-iteration frames show massively degenerate
elements — oversized triangles overlapping many others (typically spanning the annulus
hole) — which read as rendering glitches and undermine confidence in the library.

**Why this priority**: The hero GIF is the first thing every visitor sees; glitch-looking
frames directly damage the perceived quality of a mesh-quality library.

**Independent Test**: Regenerate the GIF and inspect every truss-stage frame: no element
may span the inner hole or overlap other elements at grossly oversized area.

**Acceptance Scenarios**:

1. **Given** the truss playback frames, **When** each frame is inspected, **Then** no
   rendered element crosses the annulus hole or covers an area grossly larger than its
   neighbors (no "overlapping sail" triangles).
2. **Given** the prior real-frames mandate, **When** degenerate elements are suppressed,
   **Then** every rendered node position still comes from a genuine solver iteration
   (no interpolated positions introduced).

---

### User Story 2 - Uniform convergence pacing (Priority: P1)

A visitor watches the truss stage and perceives the relaxation at a steady speed from
start to finish. Today the playback visibly accelerates toward the end of convergence
(late snapshots skip many solver iterations per frame and are held for fewer frames).

**Why this priority**: The accelerating tail makes the solver look like it "jumps" at the
end — the exact defect (#179) the real-frame playback was built to fix.

**Independent Test**: Measure mean node displacement per rendered animation frame across
the truss stage; the variation between slowest and fastest portions must be bounded.

**Acceptance Scenarios**:

1. **Given** the truss playback, **When** per-frame mesh displacement is measured, **Then**
   perceived motion is approximately constant (max/min segment displacement ratio ≤ 3).

---

### User Story 3 - Distinct stage pauses (Priority: P2)

A visitor can clearly tell when one pipeline stage ends and the next begins, because each
stage boundary holds on a settled frame slightly longer than today.

**Why this priority**: Stage legibility is the point of the GIF; cheap to implement.

**Independent Test**: Count held (unchanged) frames at each of the stage boundaries in
the rendered GIF; each must meet the minimum pause duration.

**Acceptance Scenarios**:

1. **Given** the rendered GIF, **When** each stage transition is located, **Then** a held
   pause of at least 1.5 seconds separates consecutive stages (longer than current holds).

---

### User Story 4 - Layer-by-layer peel reveal with live histogram (Priority: P1)

A visitor watches the final stage and sees the peel concept itself: starting from the
final smoothed mesh, the outermost (boundary-adjacent) layer's elements change color to
that layer's colormap color, with a pause; then the next layer inward, and so on until
the whole annulus is layer-colored. Simultaneously, the quality histogram converts in
step: the portion of each bar contributed by the just-revealed layer's elements changes
from quality coloring to that layer's color, rendered as stacked bars.

**Why this priority**: `peel_layers()` is CHILmesh's signature operation; the current
single held frame shows the result but not the concept. The synchronized histogram makes
the layer↔quality relationship visible.

**Independent Test**: Regenerate and step through peel-stage frames: layers reveal one at
a time from the boundary inward, each with a pause; histogram stacks convert in the same
frames; totals never change.

**Acceptance Scenarios**:

1. **Given** the smoothed mesh at the start of the peel stage, **When** the stage plays,
   **Then** layers recolor one at a time starting at the domain boundary and moving
   inward, with a visible pause (≥ 0.8 s) between consecutive layers.
2. **Given** the histogram during the peel stage, **When** layer *k* is revealed, **Then**
   the histogram portion contributed by layer *k*'s elements appears in layer *k*'s color
   as a stacked-bar segment, while not-yet-revealed portions remain in their prior state,
   and each bar's total height never changes.
3. **Given** the end of the peel stage, **When** all layers are revealed, **Then** the
   final frames hold on the fully layer-colored mesh + fully stacked histogram (loop
   still ends here; no re-peel).

---

### User Story 5 - Color-keyed metric annotations (Priority: P2)

In every frame that shows the histogram, a visitor can match each vertical reference line
to its metric by color: the green dotted line's metric label and value are highlighted in
the same green; a second metric gets a red dotted vertical line with its label and value
highlighted in the same red.

**Why this priority**: Today the green line floats unexplained; color-keying the text
makes the annotation self-describing at a glance.

**Independent Test**: Inspect any histogram-bearing frame: the green-line metric's text is
green; the red-line metric's text is red; the remaining metric's text is neutral.

**Acceptance Scenarios**:

1. **Given** any frame with the histogram, **When** the metric header is read, **Then**
   the metric marked by the green line is rendered in matching green text (label + value),
   and the metric marked by the red line is rendered in matching red text (label + value).
2. **Given** all animation stages, **When** frames are sampled from each stage, **Then**
   both reference lines and their color-keyed texts are present and consistent in every
   histogram-bearing frame.

---

### Edge Cases

- What happens when a mid-iteration triangulation contains only degenerate candidates in
  some region (culling could leave a visual hole)? Culling must remove at most the
  offending elements; the remaining mesh must still render.
- What happens if a peel layer contributes zero elements to some histogram bins? The
  stacked segment for that layer in those bins is empty; totals still match.
- Metric lines nearly coincide (e.g., median ≈ mean): both lines and texts must remain
  individually distinguishable (line styles/ordering must not hide one behind the other).
- Pacing resampling when the solver converges in very few iterations: the truss stage must
  still occupy enough frames to be legible (minimum stage duration).
- The GIF must remain renderable in the GitHub README (a prior defect): total size must
  not regress past the render threshold observed earlier (~4 MB budget at current
  dimensions).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Truss-stage playback MUST NOT render massively degenerate elements —
  elements spanning the annulus hole or overlapping neighbors at grossly oversized area —
  in any frame. [NEEDS CLARIFICATION: suppression method — is display-side culling of
  degenerate elements from otherwise-real solver frames acceptable (positions stay real,
  offending triangles hidden), or must the underlying solver states themselves change
  (different snapshot selection / solver settings) so no such element ever exists?]
- **FR-002**: All truss-stage node positions MUST continue to come from real captured
  solver iterations (no interpolated positions) — the prior mandate stands.
- **FR-003**: Truss-stage perceived pacing MUST be approximately uniform: the playback
  must not visibly accelerate toward convergence. Snapshot selection and per-snapshot
  hold counts must be chosen so mean node displacement per rendered frame stays within a
  3× band across the stage.
- **FR-004**: Each of the stage boundaries (Seed→Truss, Truss→FEM, FEM→Peel) and the
  pre-loop-end hold MUST include a held pause of at least 1.5 s on the settled frame —
  noticeably longer than the current holds.
- **FR-005**: The peel stage MUST start from the fully rendered final smoothed mesh and
  reveal layers one at a time, starting at the domain boundary and proceeding inward,
  recoloring each layer's elements to the layer colormap, with a pause of at least 0.8 s
  between consecutive layer reveals, ending in a held full-layer view (no re-peel).
- **FR-006**: During the peel stage the quality histogram MUST convert in lock-step with
  the mesh: when layer *k* is revealed, the histogram contribution of layer *k*'s
  elements is re-rendered as a stacked-bar segment in layer *k*'s color within the same
  frame; per-bin totals remain constant throughout. [NEEDS CLARIFICATION: before any
  layer is revealed, do un-revealed histogram portions show as the existing
  quality-colormap bars that progressively convert to layer colors (convert-in-place), or
  does the histogram reset and re-accumulate from empty as layers appear (rebuild)?]
- **FR-007**: In every histogram-bearing frame, the metric marked by the green dotted
  vertical line MUST have its label and value rendered in the same green; a second metric
  MUST be marked by a red dotted vertical line with its label and value rendered in the
  same red; any remaining metric stays neutral. [NEEDS CLARIFICATION: the header shows
  three metrics (Median, Min, Mean) and the green line currently marks the median — which
  metric is "the other" that takes the red line: Mean or Min?]
- **FR-008**: The regenerated GIF MUST still render in the GitHub README: file size must
  not exceed ~4.2 MB (≤ ~10% over the current 3.8 MB) at the current 864×396 dimensions,
  and the overall loop must remain a single loop ending on the peel result.
- **FR-009**: The generator MUST remain deterministic (fixed RNG seed) so the GIF is
  reproducible run-to-run.

### Key Entities

- **Solver snapshot**: one captured (positions, triangulation) pair from a real truss
  iteration; the unit of truss playback.
- **Animation stage**: one of Seed / Truss / FEM / Peel; owns a frame schedule and a pause
  at its boundary.
- **Mesh layer**: one concentric ring from `peel_layers()` (outer→inner ordering); owns a
  colormap color and a set of elements.
- **Quality histogram**: per-frame distribution of element quality; in the peel stage it
  becomes a stacked composition keyed by revealed layers, totals invariant.
- **Metric annotation**: a (vertical line, header text) pair color-keyed per metric
  (green metric, red metric, neutral metric).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Zero truss-stage frames contain an element spanning the annulus hole or
  overlapping neighbors at grossly oversized area (frame-by-frame audit of the rendered
  GIF).
- **SC-002**: Mean node displacement per rendered truss frame varies by no more than 3×
  between the slowest and fastest thirds of the truss stage (scripted measurement over
  the playback schedule).
- **SC-003**: Every stage boundary shows a held pause of ≥ 1.5 s (≥ 15 frames at 10 fps)
  in the rendered GIF.
- **SC-004**: The peel stage reveals every layer exactly once, boundary-first, with
  ≥ 0.8 s between reveals; the histogram's per-bin totals are bit-identical across all
  peel-stage frames while segment colors convert layer-by-layer.
- **SC-005**: 100% of histogram-bearing frames carry both color-keyed reference lines and
  matching colored metric texts.
- **SC-006**: Output GIF ≤ 4.2 MB and still animates when viewed through the GitHub
  README (manual confirmation on the pushed branch).
- **SC-007**: Two consecutive generator runs produce structurally identical animations
  (same frame count, same schedule; determinism preserved).

## Assumptions

- The four-stage sequence, dark theme, panel layout (mesh left, histogram right), 10 fps,
  and 864×396 output size are all retained; this feature only changes pacing, culling,
  the peel-stage choreography, and histogram annotations.
- "Green dotted line" refers to the existing green dashed median line; line style may be
  rendered dotted to match the operator's wording, but the governing requirement is the
  color key, not the dash pattern.
- Layer ordering for the reveal follows `peel_layers()` layer indices with layer 0 as the
  boundary-adjacent (outermost) ring, matching the boundary-inward reveal direction.
- The pause between layer reveals may be shorter than the inter-stage pause (0.8 s vs
  1.5 s) since layers are sub-steps of one stage.
- The script-local quality metric (4√3·A/Σl²) remains the histogram metric for this
  feature (swapping to `CHILmesh.elem_quality()` is a known, separately tracked concern).
- The existing `history_out=` solver hook and `deltat=0.02` converging regime remain the
  source of truss frames; this feature does not alter solver library code except, if
  clarification selects it, snapshot selection in the generator script.
- Render budget: regeneration takes ~2 min locally; binary GIF is pushed via git CLI only
  (never MCP file tools), to `development` only.
